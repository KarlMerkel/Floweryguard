# Автоматическое восстановление Discord — 31 октября 2026

## Причина и изменение

В проверенной сети TLS не отвечал на адресах Discord из системного DNS и четырёх
защищённых резолверов. Увеличение ожидания до пяти секунд и проверка нескольких
техник вне пересылки Flowery не помогли. Работающий адрес CDN отсутствовал в
обычной очереди. Ручной `hosts.txt` подтвердил маршрут, но не подходит для
автоматического режима.

После первой неудачи TLS Flowery теперь проверяет до двух резервных маршрутов
параллельно, в пределах общего бюджета повторных попыток. Используются недавние
адреса Cloudflare и два стартовых кандидата CDN (`8.6.112.0`, `8.47.69.0`). Это
резервные подсказки: без успешной проверки доверенной цепочки сертификата и имени
целевого сайта они не используются для автоматического восстановления.

Синтетический TLS-сеанс не делает HTTP-запросов, не получает пользовательские
данные и не начисляет награды. После проверки прокси отправляет исходный
ClientHello клиента в новое соединение. Клиент сам выполняет свою проверку TLS;
расшифровки или повторения запросов приложения нет.

Подсказка живёт 60 секунд, отдельно для сети, хоста и порта. Отказ реального
соединения удаляет её. Реальная передача имеет приоритет над пробами. Выбор
техники учитывает разрешённые методы и явную стратегию пользователя; `hosts.txt`
не изменяется. Пробы ограничены двумя потоками без неограниченной очереди,
повтор не чаще пяти секунд для одного назначения. После остановки результат
не публикуется. Поиск сейчас включён только для HTTPS инфраструктуры Discord.

  сертификата, параллельность, остановку и исходный ClientHello при восстановлении.
- Старый тест второстепенного Ethernet изолирован от реального шлюза компьютера;
  поведение MTU не менялось.
- Отдельный прокси из текущих исходников, без настройки Windows и без ручного
  сопоставления адресов: API — HTTP 200, 35 байт; манифест обновлений — HTTP 200,
  11508 байт; аватарка — HTTP 200, 1268 байт; `/app` — HTTP 200, 72622 байта.
- WebSocket шлюза — HTTP 101 с проверкой `Sec-WebSocket-Accept`.
- Собранный EXE прошёл `tests/smoke_frozen.py`: справка, статус, внешний конфиг
  и просмотр журнала без запуска служб. Снимки прокси, DNS и TTL совпали.
  Комплект: `dist/Flowery-v1.3.0-auto-recovery`, настройки и оценки скопированы
  из работающего `Flowery-v1.3.0-portable`. Старый процесс не завершался.
- С копией настроек: первые запросы API и обновлений — 1,594 и 4,500 секунды;
  повторные — 0,203 и 0,250 секунды. Это измерения конкретных запросов в текущей
  сети, а не обещание времени полного запуска приложения.

## Ограничения

Стартовые кандидаты могут оказаться недоступны в другой сети. Проверка сертификата
подтверждает TLS к нужному имени, но не полноту будущих файлов. Пробы остаются
отделены от обучения по настоящей передаче. Полный вход в аккаунт, загрузка всех
каналов и голос в приложении Discord автоматически не проверялись. Опубликованный
релиз этим локальным комплектом не заменён.

## Голосовое подключение

По следующему скриншоту и логу обнаружен пропуск: HTTPS-сигнализация голосового
канала на `*.discord.media` не участвовала в восстановлении. Расширена область
поиска только для этих имён и порта 443, с проверкой границ домена. UDP и выбор
голосового сервера не менялись.

Оба адреса из лога (`finland14042.discord.media`, `finland14085.discord.media`)
приняли WebSocket на двух резервных узлах с действительным сертификатом.
Отдельный исправленный прокси без `hosts.txt` также получил HTTP 101 и корректный
`Sec-WebSocket-Accept` от `finland14042.discord.media`. Обычный GET `/` на этих
серверах возвращает 403, что не означает отказ WebSocket. Авторизация голосовой
сессии и передача звука по UDP не проверены этой пробой.

Прошли 612 автономных тестов. Исправленный комплект возвращён в основную папку
`dist/Flowery-v1.3.0-portable`; текущий процесс из `auto-recovery` не прерывался.

## Ранний отказ TCP и позднее зависание передачи

Закрыты два пропуска из сверки требований:

- Если обычный TCP-маршрут не подключился, обработчик CONNECT выполняет
  ограниченный поиск проверенного резерва перед ответом 502. При успешном поиске
  продолжается исходное подключение клиента.
- Если передача получила оценку `suspect`, прежняя TLS-подсказка удаляется,
  а отдельная фоновая задача готовит маршрут для следующего соединения.
  Исходный запрос и его тело не повторяются. Короткий завершённый ответ не
  запускает поиск; старое соединение не запускает пробы в новой сети.
- На один прокси допускается одна управляющая фоновая задача без очереди и
  прежние две сетевые пробы. Остановка запрещает новые задачи.
- Проваленная пара IP/техника не участвует в ближайшем повторном поиске, пока
  действует наблюдение. Новая проверенная техника на прежнем IP может получить
  приоритет над неизвестными адресами; настоящая передача остаётся приоритетнее.

Прошли **619 автономных тестов**. Отдельная проверка из временной копии искусственно
возвращала отказ обычного `_connect_target`, затем выполняла настоящие запросы
через автоматический резерв: API — HTTP 200/35 байт, обновления — HTTP 200/11508
байт, аватарка — HTTP 200/1268 байт, шлюз — WebSocket 101 с корректным accept.
Позднее зависание, отсутствие повторной отправки данных, область действия и
порядок выбора проверены автономными воспроизведениями. Это не подтверждение
звука UDP или всех пользовательских вложений в приложении.
