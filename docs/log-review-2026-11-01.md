## Пропуск в параллельном восстановлении Discord

В `flowguard/route_recovery.py:100` метод `RecoveryRoutes.find()` использует общий
неблокирующий `_gate`. Пока идёт поиск для одного хоста, другой вызов возвращает
`None` сразу. Аналогично мешают ещё выполняющиеся задачи `_active`. Результат не
отличает занятость от проверенного отсутствия маршрута.

Автономное воспроизведение: проба для `updates.discord.com` приостановлена
через `threading.Event`; параллельный `find()` для `cdn.discordapp.com` возвращает
`None` за менее 1 мс. После завершения первой пробы тот же вызов возвращает маршрут.
Проба подменена, настоящая сеть и пользовательские кэши не использовались.

В `flowguard/proxy.py:2292` расширенный поиск вызывается после первой TLS-неудачи.
Но `_continue_tls_selection()` (строка 2106) перебирает текущие кандидаты и не
повторяет этот поиск после освобождения общего ограничения.

Это согласуется с последней сессией:

- В 00:35:33.387 резерв найден для `updates.discord.com` (строка 83).
- Одновременно начатые `discord.com` (`conn=1cb7e7820f43`) и
  `cdn.discordapp.com` (`conn=b3981c2f7021`) завершаются через 15.015 секунды
  без ответа в 00:35:47.062 (строки 177–178).
- Новые соединения находят резерв для `discord.com` в 00:35:48.405 (строка 196)
  и CDN в 00:35:53.607 (строка 302).
- Последнее из них получает TLS-ответ, но клиент сразу сбрасывает соединение
  (`client_reset`, строка 308). Полную загрузку по этой записи подтвердить нельзя.

Журнал не пишет причину пропуска расширенного поиска, поэтому связь конкретного
события с занятым `_gate` остаётся обоснованной гипотезой; сам дефект подтверждён
воспроизведением. Следующее исправление должно различать «занято» и «нет маршрута»
и повторять поиск в оставшемся бюджете, сохраняя ограничение параллельных проб,
отмену клиентом и запрет повторной передачи данных приложения.

Расширенное восстановление по-прежнему ограничено Discord на порту 443
(`_recovery_enabled_for`, `flowguard/proxy.py:1227`); BBC и SoundCloud этим
механизмом не охватываются. Это ограничение, а не доказательство, что резервные
узлы Discord подходят для этих сервисов.
